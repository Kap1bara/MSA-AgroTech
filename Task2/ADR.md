## Bounded contexts

В системе выделены следующие ограниченные контексты (DDD):

### 1. Health (Core Domain)

Контекст отвечает за:
- расчет и оценку состояния животных
- обработку событий ухудшения здоровья
- формирование health-метрик
- публикацию бизнес-событий о состоянии животных
- интеграцию с ERP по данным здоровья

Реализован как:
- health_service
- health_db (PostgreSQL)

Health владеет собственной моделью данных и является единственным источником истины по состоянию животных.

---

### 2. Feed (Core Domain)

Контекст отвечает за:
- учет кормов
- планирование кормления
- расчет расхода кормов
- прогнозирование потребности
- публикацию feed-событий
- интеграцию с ERP по данным кормов

Реализован как:
- feed_service
- feed_db (PostgreSQL)

Feed владеет собственной моделью данных и не зависит от внутренней структуры Health.

---

### 3. Sync (Integration / ACL)

Контекст отвечает за:
- прием batch-данных от Edge
- валидацию и нормализацию
- дедупликацию
- маршрутизацию данных в Health и Feed
- версионирование API синхронизации

Реализован как:
- sync_gateway
- обработчик_событий

Контекст выполняет роль Anti-Corruption Layer между Edge и доменами.

---

### 4. Edge (Supporting Context)

Работает на фермах и отвечает за:
- локальную видеоаналитику
- управление оборудованием
- локальные реакции
- работу при отсутствии интернета
- буферизацию событий
- периодическую синхронизацию

Состав:
- Видеоаналитика (C++)
- Управление оборудованием (Go)
- GSM шлюз (Go)
- Агент синхронизации (Go)
- RabbitMQ (локально)
- SQLite (локально)

---

### 5. API (Access Context)

Контекст отвечает за:
- внешний доступ Web и Mobile клиентов
- аутентификацию и rate limiting
- централизованную точку входа

Реализован через Kong API Gateway.

---

### 6. Enterprise Integration

Интеграция с корпоративной инфраструктурой:
- Kafka (шина данных)
- ERP (1С:Агро)

Публикация событий из доменных сервисов выполняется через integration adapter с гарантией commit-safe публикации (after commit или outbox pattern).

## Архитектурная модель

Архитектура построена по модели Edge + Central Server:

- Edge агент обеспечивает автономную работу на ферме
- Центральный сервер выполняет доменные расчеты
- Batch синхронизация с периодической отправкой данных
- Интеграция через Kafka и ERP
- Пользовательский доступ через API Gateway

---

## Принятые архитектурные решения

### Видеоаналитика - C++

Решение: сервис реализуется полностью на C++.

Обоснование:
- максимальная производительность
- минимальный runtime overhead
- эффективная работа с OpenCV
- снижение требований к железу
- экономия при масштабировании

Компромиссы:
- сложность разработки
- более дорогие специалисты

Риски:
- дефицит компетенций
- увеличение time to market

---

### RabbitMQ (Edge)

Обоснование:
- асинхронная коммуникация между сервисами
- буферизация событий
- поддержка оффлайн режима
- легковесность
- стандарт AMQP
- простота интеграции

Компромиссы:
- ниже throughput по сравнению с Kafka

Риски:
- необходимость контроля очередей при перегрузке

---

### Edge сервисы - Go

Обоснование:
- простая конкурентность
- низкий memory footprint
- удобство сетевого кода
- простота деплоя

Компромиссы:
- наличие GC
- меньшая выразительность для сложной бизнес логики

Риски:
- усложнение при росте логики

---

### Связь Edge - Центр - REST (HTTPS)

Обоснование:
- периодическая синхронизация
- отсутствие streaming требований
- устойчивость к NAT и мобильным сетям
- простота эксплуатации

Почему не gRPC:
- нет необходимости в постоянном соединении
- избыточность для batch модели

Компромиссы:
- JSON менее эффективен чем protobuf

Риски:
- возможная необходимость бинарной сериализации при росте объемов

---

### Event Processor - Go

Обоснование:
- технический pipeline
- высокая пропускная способность
- I/O нагрузка
- горизонтальное масштабирование

Компромиссы:
- не подходит для сложной бизнес логики

Риски:
- риск смешения технической и доменной логики

---

### Health и Feed сервисы - Java/Kotlin

Обоснование:
- сложная предметная область
- выразительная модель
- зрелая экосистема
- поддержка транзакций

Публикация в Kafka выполняется через integration adapter после успешного commit транзакции (after commit или outbox pattern).

Компромиссы:
- больший memory footprint
- необходимость JVM tuning

Риски:
- рост инфраструктурных затрат

---

### API Gateway - Kong

Обоснование:
- аутентификация
- rate limiting
- централизованный контроль доступа
- готовность к SaaS модели

Компромиссы:
- дополнительный инфраструктурный слой

Риски:
- усложнение DevOps процессов

---

### PostgreSQL

Обоснование:
- ACID гарантии
- надежность
- поддержка сложных запросов
- зрелость экосистемы

Компромиссы:
- ограниченное вертикальное масштабирование

Риски:
- необходимость шардинга при значительном росте числа ферм

---

## Итог

Разделение домена на Health и Feed признано предпочтительным решением, так как:

- соответствует DDD
- снижает связанность
- упрощает масштабирование
- обеспечивает долгосрочную устойчивость архитектуры
